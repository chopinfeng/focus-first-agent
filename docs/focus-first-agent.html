Focus-First Agent Framework

一个把人的注意力当作最稀缺调度资源的 Agent 框架。Agent 的断点不是人的断点，这个框架负责把两者对齐。

框架的最小可见单元：一条 AttentionRequest 在收件箱中的样子。人看到的是"为什么需要我、不答会怎样、按哪个键"，而不是 transcript。

命题

现有 Agent 框架优化 token、时延和正确率，人的注意力只是副作用。所有主流 SDK 都是逐条打断、无限等待、无预算、无时机感。FFA 在 Agent 运行时和人之间插入一个注意力内核，让每一次"需要你"都经过调度。

三条设计信念，全部来自调研：

  • 打断是效用计算，不是默认行为。自主执行、发起对话、什么都不做，三者由"推迟代价 vs 打断代价"决定，并随人的状态变化（Horvitz 1999/2003）。
  • 可逆性比风险等级更有杠杆。生产环境仅 0.8% 的动作不可逆（Anthropic）；可逆动作应当直接做并记录回滚点，用事后审计替代事前审批。
  • 人看结论和证据，不看过程。子 Agent 只返回蒸馏结论、diff-first、预览优先，是所有成熟产品收敛出的同一原则。

学术研究给出的硬约束

打断有时机

defer-to-breakpoint：推迟到子任务边界投递，恢复更快、挫败更少，粗粒度断点优于细粒度（Iqbal & Bailey 2008/2010）。FlowLight 用键鼠活动推断可打扰性，中断减少 46%。

周边 vs 中心

平静技术：信息驻留注意力周边，需要时才移到中心（Weiser & Brown 1996）。可扫视性是关键属性；状态用颜色和位置编码，不用文字通知。

一人能管几个 Agent 有公式

FO ≈ NT/IT + 1，忽视时间除以交互时间（Olsen & Goodrich）。操作员利用率超过 70% 后绩效衰退（Cummings & Guerlain 2007）。提高 fan-out 的两条路：更自主，或更好的请求界面。

完全自动化最危险

out-of-the-loop 导致情境意识下降、接管更慢（Endsley & Kiris 1995）。目标是信任校准而非信任最大化（Lee & See 2004）。注意力残留：切换前收尾能清除残留（Leroy 2009）。

现有框架的八个空白

逐个核对 LangGraph、HumanLayer、OpenAI Agents SDK、Claude Agent SDK、Vercel AI SDK、Microsoft Agent Framework、CrewAI、Temporal、AG-UI、A2A、MCP 后发现：

  1. 决策请求没有统一 schema：question、options、default、deadline、consequence、reversibility 从未作为一个对象出现。
  2. 没有批处理、digest、静默时段、合并同类审批。
  3. SDK 层 interrupt 无限等待，没有"超时选安全默认"。只有 Temporal 一类持久工作流有 timeout。
  4. 信任增长没有量化模型；OpenAI 的 always_approve 和 Claude 的 PermissionRequest 追加规则都是手动。
  5. 没有 PagerDuty 式升级阶梯对接 Agent 事件。
  6. MCP 已有 readOnlyHint / destructiveHint，但没有框架用它驱动 ask-vs-act。
  7. 面向人的可观测性仍是日志；没有 plan-of-record、偏差、"what I need from you"的结构化事件。
  8. 注意力预算本身不被建模。没有框架把"本小时最多打断 N 次"或"用户当前状态"作为调度输入。

FFA 的每个组件都对应至少一个空白。

架构

六个核心抽象

抽象是什么填补的空白
TaskCard委派时一次写清：goal、scope、constraints、done_criteria、risk_class，以及一份 attention_contract（本任务打断预算、deadline、允许渠道、拿不准时是"推荐并继续"还是"问并等"）。#7、#8
AttentionRequest框架的"系统调用"。任何 SDK 的 interrupt、approval、elicitation、notification 都先翻译成它。#1
AttentionKernelPolicy、Scheduler、Budget、Timeout 四个子模块，按顺序处理每个 AR。#2、#3、#5、#8
HumanStateModel本地推断四态 FOCUS / BREAKPOINT / IDLE / AWAY。信号：键鼠活跃度、前台应用、日历、显式 /focus、上次打开收件箱时间。只输出枚举，不存原始活动。#8
EvidencePacket任务收尾唯一交付物：结论、变更摘要、验证证据、风险标签、我做的假设、未决问题、回滚方式。由独立 verifier 子 Agent 打标签。#7
AttentionLedger每个 AR 的生命周期：发出、投递时的状态与渠道、结果、耗时。同时是信任账本和指标源。#4

AttentionRequest schema

{
  "id": "ar_01J…", "task_id": "t_42", "agent_id": "claude-code:worktree-3",
  "kind": "approval",              // notify | question | approval | review | escalation
  "headline": "要删除 3 个旧 migration 文件，不可逆",   // ≤ 120 字符：为什么需要你
  "context": {                     // 恢复上下文，消除注意力残留
    "you_were": "在 review PR #812",
    "i_did":    "迁移了 auth 路由，测试 41/41 通过",
    "i_need":   "确认能否删除 2023 年的 3 个 migration",
    "blast_radius": "db/migrations/2023_*.sql，影响本地与 CI，不影响生产"
  },
  "options": [
    { "id": "delete", "label": "删除", "recommended": true, "consequence": "CI 需重新跑 12 min" },
    { "id": "keep",   "label": "保留并加 deprecated 注释" },
    { "id": "later",  "label": "先跳过，任务结束时再问" }
  ],
  "default": { "option_id": "keep", "apply_after": "PT30M" },   // 无人回应时的安全默认
  "risk": { "level": "P1", "reversible": false, "scope": ["fs"] },
  "urgency": "soon",               // now | soon | whenever
  "cost_estimate": { "interaction_seconds": 40 },
  "confidence": 0.8,               // Agent 对推荐项的置信度
  "ttl": "PT4H", "on_expire": "apply_default",   // apply_default | block | escalate
  "batch_key": "fs.delete:db/migrations",        // 同 key 合并成一次决策
  "evidence": ["diff://…", "log://test-run-88"]
}

高亮字段是现有框架中集体缺席的：default 与 on_expire 保证永不无限阻塞，batch_key 让 12 次文件写入变成一次批准，context 四行让人不必回忆自己在做什么。

决策策略：ask vs act

评估顺序借鉴 Claude Agent SDK 的六步权限模型，加入账本和效用两层：

硬 deny 规则 → 硬 ask 规则 → 信任账本（自动放行 / 自动拒绝） → 效用计算 → 分类器兜底 → 默认 ask

风险 × 可逆性矩阵

可逆不可逆
范围内，低爆炸半径ACT 记录回滚点，进 digestASK 带安全默认，延迟到断点，可合并
范围外或外部副作用ACT + notify(soon)ASK(now) 阻塞，超时升级
P0：生产、资金、删除、对外发消息ASK(now)ASK(now) 不可设默认放行，超时即 block

效用计算

surface_now  if  P(need_human) × Cost(wrong)  >  Cost(interrupt | state) + Cost(resume)
defer        if  上式不成立 且 存在安全默认
act          if  P(need_human) < act_threshold(risk) 且 reversible

打断成本随状态取值：FOCUS 取 Parnin 的 10 到 15 分钟量级，BREAKPOINT 取 1 到 2 分钟，AWAY 取渠道成本。阈值按（用户，动作类）从账本学习。

信任账本升级规则

  • 键是（用户，动作类），例如 fs.write:src/**、shell:pnpm test、git.push:feature/*。
  • 连续 10 次 approve 且 0 次 undo，自动升为 auto_allow，并在 digest 里告知"已自动放行，可撤销"。
  • 任何一次 reject 或 undo 立即降级并重置计数。
  • P0 动作类永不自动放行。账本对用户可见可编辑，一行命令回到"全部询问"。

任务生命周期

  1. Intake：填 TaskCard。框架用一次结构化表单把所有可预见的决策前置：多选、推荐项、"不回答则按推荐执行"。
  2. Plan-of-record：计划是对象不是文本。执行期只有偏离计划才生成 question 类 AR，按计划走的不打扰。
  3. Execute：默认静默。SDK 事件经适配器变成 AR 进内核。周边状态灯实时反映 working / blocked / needs-you / done。
  4. Verify：独立 verifier 跑 done_criteria，打风险标签，生成证据。不通过则回到上一步，不打扰人。
  5. Deliver：EvidencePacket 作为 review 类 AR 进收件箱。P2/P3 且验证通过的可配置为自动合并加 digest 通知。
  6. Learn：账本回写阈值、信任、渠道偏好。

呈现面

周边状态

每个 Agent 一个可扫视的状态点，放在菜单栏、终端状态行或 IDE 状态栏。灰是 working，黄是 blocked，橙是 needs-you，绿是 done。绝不弹窗。

异常收件箱

唯一需要人"看"的地方。排序按 urgency、deadline、风险、价值。每项是 headline、四行 context、带默认高亮的选项、单键回答，并显示不回答会发生什么和剩余 TTL。

Digest

一屏摘要：已自动放行的可逆动作（带 undo）、进度、账本升级告知。周期性推送保住情境意识。

渠道与 transcript

终端、桌面、手机 push、Slack。同一 AR 跨渠道同步，任一处回答即全局解决。transcript 降级为审计视图，默认折叠。

适配器

不重造运行时。每个来源只做两件事：把事件翻译成 AR，把 AR 决议翻译回恢复调用。

风险与对策

风险对策
Out-of-the-loop：自动化太多，人失去情境意识周期性一屏 digest；关键阶段保持"提议 + 确认"；EvidencePacket 强制列出假设
自动化自满：信任账本让人不再看undo_rate 与 rubber_stamp_rate 触发"抽查"AR；账本升级在 digest 中显式告知
过度抑制：把真正紧急的压进 digestP0/P1 永远可穿透静默；on_expire 为 block 时不可被预算覆盖
状态推断隐私全部本地计算，只输出四态枚举，不存原始活动
Agent 虚报进度，调研中上升最快的错位verifier 独立于执行 Agent；done_criteria 必须可机器验证
多工具上下文丢失TaskCard、plan-of-record、ledger 是跨运行时共享的持久对象

待确认的假设

  • 首个运行时以 Claude Code / Claude Agent SDK 为主，hooks 与权限模型最完整，适配成本最低。
  • 首个用户是单个开发者同时跑 2 到 5 个 Agent 的场景；团队升级阶梯放到 P3。
